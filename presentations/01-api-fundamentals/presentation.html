Chapter 1 · Claude and OpenAI API fundamentals

One HTTP call
under everything

The Claude Messages API and the OpenAI Responses API: what you send, what comes back, and the decisions you own at this layer.

20 minutes · Claude + OpenAI @eldan.nomad@eldan_nomad@eldan_nomadeldan-abdrashim
Everything later in this course (tool use, agents, MCP, Claude Code, Codex) sits on one HTTP call. On Claude that is POST /v1/messages, on OpenAI POST /v1/responses. In twenty minutes we take both apart side by side: the request, the response, how to tell why generation stopped, who owns conversation state, and how tokens, models and effort drive cost.
Why this matters

Most production incidents start at this layer

Symptom

“The bot forgot”

The app didn’t resend history, or chained from the wrong state.

Layer: conversation state

Symptom

“The agent never stopped”

The loop parsed the model’s prose instead of the stop signal.

Layer: stop_reason / status

Symptom

“The bill doubled”

Growing history, hidden thinking tokens, the wrong model tier.

Layer: tokens, model, effort

Tools, agents, MCP and coding agents are all built on this one call. Get the contract right first.
Three incidents you will see in real projects, and each one traces back to a wrong assumption at the API layer, not to the model. The bot forgets because the app did not resend history. The agent loops forever because the code checked whether the reply had text instead of reading the stop signal. The bill doubles because history grows every turn and thinking tokens are billed as output. Everything in the next twenty minutes is about avoiding these three.

Part 1 · The request

One endpoint. Features are parameters.

ClaudeMessages API
client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=16000,      # required
    system="You are concise.",
    messages=[{"role": "user",
               "content": "What is an API gateway?"}],
    output_config={"effort": "low"},
)
OpenAIResponses API
client.responses.create(
    model="gpt-6-luna",
    max_output_tokens=2000,  # optional
    instructions="You are concise.",
    input="What is an API gateway?",
    reasoning={"effort": "low"},
    store=False,              # default: True
)
Both output ceilings include thinking / reasoning tokens. Set one too low and the model can spend it all thinking, then return no visible text.
Same shape on both sides: one endpoint, and tools, structured output and effort are just parameters on it. Three differences to call out. Claude requires max_tokens; OpenAI's max_output_tokens is optional. Claude's operator instructions go in the top-level system field; OpenAI uses instructions or a developer message. And OpenAI stores responses by default for 30 days, so store=False is a deliberate choice for sensitive workloads. On both, the ceiling includes thinking, so keep it generous: around 16K on Claude non-streaming, and OpenAI suggests reserving at least 25K tokens when you start with reasoning models.
Part 1 · The response

The reply is a typed list, not a string

Clauderesponse.content
thinkingtexttool_use
text = "".join(b.text for b in resp.content
               if b.type == "text")
OpenAIresponse.output
reasoningmessagefunction_call
text = resp.output_text  # joins output_text
# tools, refusals: iterate resp.output by type
content[0].text and output[0].content[0].text break the moment thinking, reasoning or a tool call comes first. Filter by type.
HTTP errors are not stop signals: catch typed exceptions. Both SDKs retry 408, 409, 429 and 5xx twice with backoff.
The single most common bug in first integrations. On current models thinking is on by default, so Claude's first block is often a thinking block with no text attribute; on OpenAI the first output item is usually a reasoning item. output_text is fine for "just give me the answer" code, but wrong for anything that must react to tool calls, refusals or truncation. Errors are separate: a failed request is an HTTP error and a typed exception such as RateLimitError; a successful one is HTTP 200 with a stop signal. Note: a 429 from a spend or quota limit will not go away by retrying.
Part 1 · Roles and instructions

Where operator instructions live

Claude
  • system is a top-level field. Resend it on every call.
  • messages alternate user / assistant. Tool results ride in a user turn.
  • Mid-conversation system messages: newest models only.
  • Prefill (ending on an assistant turn) returns 400 on 4.6+ models.
OpenAI
  • input is a list of items: messages, reasoning, function calls.
  • developer / system roles outrank user.
  • instructions apply to this request only.
  • Not carried by previous_response_id. Resend every turn.
Scope every rule. “Always verify the customer” makes an agent call the lookup tool on every turn, opening-hours questions included.
Both vendors separate operator authority from user input, but the mechanics differ. Claude: the system field is persistent only because your code resends it. Mid-conversation system messages exist on Opus 5.5, Sonnet 5.5 and Fable models but are rejected by Haiku 4.5 and older; never put untrusted text there. Prefill is gone on current models: use structured outputs. OpenAI: classic trap, the team switches to previous_response_id and the tone rules stop working from turn 2, because instructions are not carried over. Last point applies to both: absolute, keyword-style rules create unintended tool associations. If a tool is over-used despite a clear description, check the system prompt wording first.
Part 2 · Why it stopped · Claude

Claude: one field, seven answers

ValueMeaningYour code
end_turnFinished naturallyReturn the answer
tool_useWants your toolsRun every call, send all results in one user turn, call again
max_tokensOutput budget hit, truncatedRaise the limit or stream. Never run a half-written tool call
model_context_window_exceededWhole window is fullShrink the input. A bigger max_tokens does nothing
pause_turnServer tool loop pausedSend the assistant turn back unchanged
stop_sequenceYour custom stop stringApp logic; read resp.stop_sequence
refusalModel or classifier declinedCheck before reading content; explain or fall back
Agent loop: continue while tool_use, stop on end_turn. Never search the prose for “done”.
stop_reason is the only reliable control signal. The guide lists four values; the current API has seven. The pair to remember: max_tokens and model_context_window_exceeded both mean truncated output, but the fixes are opposite. The first means too few output tokens; the second means the whole context is full, so you remove input. Refusal arrives with HTTP 200 and possibly empty content, so check it before reading content; stop_details explains the category. A fixed iteration cap is a good safety net, never the primary stopping rule.
Part 2 · Why it stopped · OpenAI

OpenAI: three places to look

1

status

completed · incomplete · failed · cancelled · queued / in_progress

2

incomplete_details

.reason: max_output_tokens or content_filter

3

Output item types

function_call → run tools · refusal part → fall back · text → answer

HTTP 200, empty answer? incomplete + max_output_tokens + no text = the budget went to reasoning. You paid and got nothing. Raise the budget or lower effort; don’t rewrite the prompt.
Agent loop: continue while the response has function_call items. Text can arrive alongside a tool call.
OpenAI has no single stop_reason. A tool request is a completed response that contains function_call items, a refusal is a content part inside a message, and truncation is status incomplete with a reason. The empty-answer trap is the classic exam and production question: the request succeeded, output_text is empty, and the cause is a max_output_tokens budget consumed by reasoning. For loops, checking whether output_text is non-empty is wrong, because the model can write a preamble and call a tool in the same response.

Input tokens, cost and latency grow every turn.

history.append({"role": "user",
                "content": text})
resp = client.messages.create(
    model=MODEL, max_tokens=16000,
    system=SYSTEM, messages=history)
# keep full blocks, not just text
history.append({"role": "assistant",
                "content": resp.content})
“It forgot what I said two turns ago” = the app didn’t resend history. Not a window problem. There is no session_id.
The Messages API keeps nothing between calls: no session, no server-side history. Every turn you resend the system prompt, tools and the whole conversation. Append resp.content, not just the text, so thinking and tool_use blocks survive. Two turns of chat cannot overflow a 1M window, so a forgetful bot is almost always a missing-history bug. To keep long chats affordable: prompt caching for the stable prefix, and a hybrid history of structured facts, a summary of old turns and recent turns verbatim.
Part 3 · Conversation state · OpenAI

OpenAI: decide who owns the state

Your app

Stateless

store=False, replay every output item yourself.

Stored: nothing
Fits: ZDR, compliance, portability

OpenAI · 30 days

Chained

Send previous_response_id + the new input.

Stored: each response
Fits: short sessions, least code

OpenAI · until deleted

Durable

Conversations API, conversation=conv.id.

Stored: conversation + items
Fits: threads across devices, jobs

Server-side state is not cheaper: the whole chain is billed as input every turn. It is a data-retention decision, and store defaults to true.
This is the biggest architectural difference from Claude. Rules worth memorizing: previous_response_id and conversation cannot be combined. Over HTTP, chaining needs a stored response, so store=False plus previous_response_id is unsupported; replay history instead. Deleting a conversation does not delete its items; delete the items first. With Zero Data Retention, store is always false and the Conversations API is not eligible, so a ZDR design is stateless with compaction. And switching to previous_response_id is not just a refactor: it moves conversation data into OpenAI storage for 30 days. Check with whoever owns retention.

Tool-result bloat. A tool returns 40 fields, you need 5. Trim before you append.

“Switch to a bigger window” is usually the wrong fix. Accuracy degrades as context grows.
Everything counts toward the window: system prompt, tool definitions, every message and tool result, and this turn's output including thinking. On current Claude models, earlier thinking blocks are kept and count as input. Both vendors now offer around a million tokens, which tempts people to dump everything in. Anthropic calls the degradation context rot. The three failure patterns apply to both vendors unchanged. Overflow behaviour: Claude returns 400 if the input alone is too long, and model_context_window_exceeded if generation fills it. OpenAI returns 400 by default; truncation auto silently drops the oldest items, which often hold the critical facts.
Part 4 · Tokens

Count before, measure after

Claudecounting is free
# before
client.messages.count_tokens(
    model=MODEL, system=SYSTEM, messages=msgs)
# after
resp.usage.input_tokens, resp.usage.output_tokens
resp.usage.cache_read_input_tokens
OpenAIcounts formatting tokens too
# before
client.responses.input_tokens.count(
    model=MODEL, instructions=RULES, input=items)
# after
resp.usage.output_tokens_details.reasoning_tokens
resp.usage.input_tokens_details.cached_tokens

Thinking is billed as output on both, and counts against the output ceiling.

Tokenizers differ. Claude 4.7+ models produce ~30% more tokens. No tiktoken, no chars ÷ 4.

GPT-6 over 272K input: 2× input, 1.5× output, for the whole request.

Use the provider's counting endpoint with the model you will actually call; counts are model-specific. Claude's count_tokens is free with its own rate limit; it rejects server tools and URL-sourced files, so read usage after the call for those. OpenAI's input_tokens.count accepts the same input as create, but not generation options like max_output_tokens or store. A 1M window is available on GPT-6, but filling it past 272K is a pricing decision. Caching: Claude cache reads cost 10% of input on most models; OpenAI caching is automatic from 1,024 tokens and up to 95% cheaper. Neither lowers the size of the context.

The cheapest list price is not automatically the cheapest system: a model that needs retries or extra turns costs more per completed task. Batch processing halves all of these on both vendors. Re-check pricing pages before any real estimate. Also note Haiku 4.5's retirement commitment is only "not sooner than October 15, 2026"; check the deprecations page before building on it.

Three levers interact: model tier, effort, and architecture, such as a cheap model for routing and a strong one for synthesis. On OpenAI each model accepts only a subset of effort values, and an unsupported one returns 400: Astra has no none, 6.1 Sol starts at low, Luna supports none for latency-critical work. Haiku 4.5 does not support effort at all. OpenAI's fast-front pattern: a cheap model chats with the user and delegates heavy tasks to Astra, so you pay flagship prices only where it pays off. Wrong answers on the exam: "use the biggest model to be safe" and "pick the largest context window".
Part 5 · Non-determinism

Same request, different answer. Design for it.

Wrong twice

temperature=0 for stable tests

Claude: non-default temperature, top_p, top_k return 400 on models after Opus 4.6.

OpenAI: remove temperature and top_p on GPT-6 unless effort is none.

And it never guaranteed identical output anyway.

  • Test properties: parses, matches schema, right label, has the facts.
  • 3–5 runs per example. Report a pass rate, not one demo.
  • Structured outputs fix the shape. Validators check the content.
  • Pin and log model ID, prompt version, effort, tools, request ID.
  • Same answer every time? Store it in your app.
Each token is sampled, and with adaptive thinking the model also chooses how much to reason, so identical requests can produce different text, different tool calls or occasionally a different label. Prompt caching does not change this; it reuses the processed prefix, not the answer. On OpenAI the Playground is the place to explore, but a prompt that looked right on three inputs is not evidence: move it into a versioned prompt builder in your repo with an eval set. Saved prompt objects (v1/prompts) shut down on 2026-11-30.
Part 5 · Production access

Getting the call into production

Claude
  • SDK over raw REST: auth, retries, typed errors, request IDs.
  • AsyncAnthropic + a semaphore for fan-out under rate limits.
  • Bedrock, Google Cloud, Foundry: new client class and model-ID map, same body.
  • Batches and Models API: Claude API only.
OpenAI
  • stream=True: typed events such as response.output_text.delta.
  • background=True + polling or webhooks for multi-minute jobs.
  • WebSocket mode: up to ~40% faster with 20+ tool calls.
  • Chat Completions is legacy. Assistants API retired 2026-08-26.
Never blind-retry a timed-out long job: each retry starts and bills a new run. Stream long output; use background mode or batches instead.
Claude: the SDK is a typed wrapper over one POST with three headers, so raw HTTP is only for languages without an SDK or for debugging. Async does not make one call faster; it keeps more in flight. On cloud platforms the request body stays the same, but the client class, model ID and credentials change: Bedrock adds the anthropic. prefix, Foundry uses your deployment name. Features differ too, so check parity before you design. OpenAI: background mode exists for reasoning that can take minutes behind proxies with short timeouts. Chat Completions is still supported, but GPT-6 Astra and 6.1 Sol need the Responses API for tool calling.
