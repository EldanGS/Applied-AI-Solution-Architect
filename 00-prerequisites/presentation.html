Part 1 · Software prerequisites

Software skills: the floor, not the goal

Code

Typed, async Python. Read TypeScript fluently: SDK and MCP samples.

APIs & contracts

HTTP, REST, status codes. JSON Schema + Pydantic: the contract for tools and outputs.

Git & review

Branch, small commits, PR, review. No secrets in history.

Testing & CI/CD

Automated tests, pipelines, GitHub Actions.

Cloud & containers

Docker, one major cloud, infrastructure as code.

Security basics

Secrets, least privilege, OAuth and SSO concepts.

Bar: read code you didn’t write, ship small, know which errors to fix (400, 401, 404) vs retry (429, 5xx, 529).
Keep this short. Python is the working language; TypeScript is reading fluency because many SDK and MCP examples use it. Git and CI matter because coding agents run inside pipelines. Errors: client errors are fixed, transient errors are retried with backoff. Trap: a 429 from a monthly spend cap has no retry-after header and keeps failing; alert a human. JSON Schema is the shape behind tool inputs, structured outputs and MCP tools; generate it with Pydantic instead of hand-writing it. Plus-level extras: SQL, queues and events, Kubernetes.
Part 1 · AI prerequisites

AI fundamentals: intuition, not a PhD

ML basics

Training vs inference. Train / test split, overfitting. Why held-out data becomes your eval set.

How LLMs are made

Pretraining → instruction tuning → RLHF. Explains the knowledge cutoff and the confident tone.

Transformer intuition

Tokens → embeddings → attention → next-token probabilities. Concept, not derivation.

Embeddings & vectors

Meaning as a vector. Cosine similarity, nearest neighbours. The basis of RAG and search.

Probability & metrics

Sampling and variance. Precision, recall, F1. Pass rate over N runs, not one demo.

Data handling

pandas and SQL. Clean, sample, label a small gold set. Most AI work is data work.

Not required: training models from scratch, heavy math, CUDA. Fine-tuning comes last, after prompting, RAG and evals.
The AI side of the floor. You are an engineer who uses models, not a researcher who trains them, so you need intuition. ML basics: held-out data is the idea behind every eval set. How LLMs are made explains behaviour: pretraining on text gives knowledge with a cutoff date, instruction tuning and RLHF make the model helpful and fluent, which is why it sounds confident even when it is wrong. Transformer intuition: attention lets each token look at every other token in the context. Embeddings and cosine similarity are the whole of semantic search. Metrics: precision, recall and F1 for classification, pass rate over several runs for generation. And daily tool fluency: use Claude Code, Codex or ChatGPT for real work every day. Good free starting points: Andrej Karpathy's Intro to LLMs, 3Blue1Brown's neural network series, Google's ML Crash Course.
Part 2 · Tokens

Models read tokens, not words. You pay in tokens.

Rule of thumb for English: ~4 characters ≈ 0.75 words ≈ 1 token. Code and other languages differ.

Billing

Per million input and output tokens. Output is ~5× the price of input.

Limits

Context window, max_tokens and rate limits are all counted in tokens.

Tokenizers differ

By vendor and by model generation. Never reuse another model’s count.

Hidden tokens

Tool definitions, system prompts and thinking all count. Thinking is billed as output.

Count first: client.messages.count_tokens(…) · client.responses.input_tokens.count(…)
Why you care: billing, limits, and the fact that tokenizers differ. Newer Claude models produce roughly 30% more tokens for the same text than older ones. Hidden tokens are where budgets leak: a big tool list or heavy thinking can dominate the bill.

Window = system + tools + history + documents + the output itself.

  • Cost and latency grow with conversation length, unless you trim, summarize or cache.
  • More context isn’t better. Slower, pricier, and details in the middle get missed. Curate.
  • If the model must know it, it’s in the window or reachable by a tool.
The model remembers nothing between calls. Every turn you resend system prompt, tools and history. Current flagship models have windows around 1M tokens; that tempts people to dump everything in. Lost-in-the-middle and cost say: curate.
Part 2 · Generation

One token at a time, so test properties, not strings

Contextinput + tokens so far
→
Probabilitiesfor every next token
→
Sample one
→
Appendrepeat until stop

Latency

Output tokens, including thinking, drive response time. Hence streaming.

Variation

Same prompt, different text. Steer with effort, not temperature.

No take-backs

An early wrong token shapes the rest. Reason first, then answer.

Truncation

Check stop_reason / status. Always.

Test properties: it parses · matches the schema · contains the required facts · stays under the limit · pass rate over N runs.
This one loop explains latency, variation, brittleness and truncation. The practical takeaway: never assert exact output strings. Use property checks plus a pass rate, and a small eval set you re-run on every prompt or model change. Steering: on Claude 4.7 and later, non-default temperature, top_p or top_k return a 400; set reasoning depth with output_config effort (low to max), and OpenAI exposes the same idea as reasoning. Responses can start with thinking blocks, so select output by block type, never content[0].
Part 2 · Grounding

Hallucination is fluent output that isn’t grounded

1

Ground

Put the source in context or give a retrieval tool. Answer only from it.

2

Give an exit

Allow “I don’t know” and nullable fields.

3

Ask for evidence

Quotes and citations you can check in code.

4

Validate

Schema + business rules. Retry with the error as feedback.

5

Measure

A small eval set and a trend line, not spot checks.

The model is optimized for plausible continuations, not verified ones. Your system supplies the verification.
The model is not a database. Five mitigations that show up in every real project. Emphasize 2 and 4 together: a nullable schema plus a validation-and-retry loop is the cheapest big win.
Part 3 · Prompt & context engineering

A prompt is code: structure it, version it

Put it inWhat goes there
systemRole, stable rules, criteria, examples, output format
userLong documents first, the question last
Tool descriptionWhen to use it, what it returns, its limits
tool_resultData only. Untrusted, never instructions
  • Clear and direct. Would a colleague with no context get it?
  • One XML tag per content type: <documents>, <examples>
  • Explicit criteria, plus the reason behind each rule
  • Few-shot examples for format and edge cases
  • Template + version ID, logged with every request
Cache-friendly order: static prefix first (system, examples, policy), per-request parts last. Cheaper and faster.
Context engineering is deciding what goes where. Each place carries a different authority: the system prompt is the operator, tool results are third-party data. Treat prompts like code: modular, versioned, tied to eval runs. Putting stable content first lets prompt caching cut cost and time to first token.

Tool use is where a model stops being a text generator and starts acting on real systems. The model never runs your code; it returns a request. Same loop on both vendors, only the names differ. Reliability comes in layers: good descriptions for tool choice, strict schemas for well-formed arguments, and your own code for business rules and approvals.

Measure retrieval and answer quality separately, so you know which stage fails.
An embedding is a vector representing meaning; nearby vectors mean similar text. RAG finds the most relevant chunks and puts them in the context window: a concrete way to ground the model. In practice, hybrid search (semantic plus BM25 keyword) and reranking beat pure vector search. Vendor note: Anthropic has no first-party embedding model (its docs point to Voyage AI); OpenAI offers embeddings, vector stores and a hosted file_search tool.
Part 3 · Agents

Use the simplest thing that works

Start here

Single call

One well-prompted request. Most problems end here.

Steps known

Workflow

You hard-code the sequence of calls. Predictable, testable.

Path unpredictable

Agent

A model in a loop with tools. Always set a max-turns limit.

Agents trade predictability, latency and cost for flexibility. Climb only when forced.
From Anthropic's Building effective agents: workflows are orchestrated by your code, agents direct their own process. Start with a single call, move to a workflow when the steps are known, and use an agent only when the path really cannot be predicted. Runaway tool loops are the most common surprise bill.

These five workflow patterns come from Anthropic's Building effective agents and map directly onto real projects. Prompt chaining for fixed pipelines, routing to send easy cases to a cheap model, parallelization for speed or confidence, orchestrator-workers for research-style tasks, evaluator-optimizer when quality can be judged against clear criteria.
Part 3 · Guardrails

Prompts guide. Code enforces.

≈ 50 / day

An agent that verifies identity 99.5% of the time, at 10,000 refund chats a day, still lets about 50 unverified refunds through. Every day.

Use it for
Prompt guidance
probabilistic		Tone, judgment, when to offer what
Code enforcement
deterministic		Ordering, identity, money limits, compliance, irreversible actions
Human approvalDestructive or high-value actions
Gate state comes from tool results, never from what the model says.
The most important design rule for agents that act on real systems. Better prompts lower the failure rate; they never make it zero. When a single violation has financial, legal or safety consequences, put the rule in code: a prerequisite gate or hook that blocks the refund tool until identity is verified, and a hard limit that routes large refunds to a human.

Part 4 · Evals

If you can’t measure it, you can’t ship it

Success criteriaper use case
→
Datasetreal, representative
→
Graderscode + LLM judge
→
Release gateevery prompt or model change
→
Monitoronline, by segment

Code graders first

Parses, matches schema, right label, has the facts. Cheap and exact.

Calibrate the judge

Check an LLM judge against human labels before you trust it.

Eval before prompt

Write the test set first. Then every change is a measured decision.

Evals are the most requested technical skill in applied AI work, because they let you say 'this works' to a customer, switch models safely and justify a cheaper model. Report a pass rate over several runs, slice results by segment, and gate every prompt or model change on the eval set.
Part 4 · Trade-offs

Cost, latency, reliability: pick your levers

Cost
  • Curate context first
  • Prompt caching
  • Batch API, ~50% off
  • Smaller model, lower effort
Latency
  • Stream the output
  • Run independent calls async
  • Shorter outputs
  • Route easy cases to a fast model
Reliability
  • Retries + backoff + jitter
  • Idempotency keys on side effects
  • Schema validation
  • Fallbacks and timeouts
Curated context is the one lever that improves all three. Downgrade a model only after the evals agree.
You can usually buy one of cost, latency and reliability with the other two. Batch is the big cost lever when latency doesn't matter. Streaming changes perceived latency only. Shorter, curated context is cheaper, faster and often better. Reliability: both SDKs retry for you, so tune max_retries and timeout. A timeout does not say whether a side effect ran, so refunds, emails and tickets need an idempotency key.

Part 4 · Operate it

You can’t defend what you can’t see

Log on every model call 
{
  "model": "claude-sonnet-5-5",
  "prompt_version": "refund-v12",
  "request_id": "req_…",
  "latency_ms": 1840,
  "input_tokens": 1250, "output_tokens": 310,
  "stop_reason": "end_turn",
  "estimated_cost_usd": 0.0056,
  "attempt": 1
}
Security basics
  • Prompt injection: documents, web pages and tool results can carry instructions. Treat them as data.
  • Least privilege: read-only tools by default.
  • Secrets in a vault, one key per environment.
  • Privacy: redact PII before storing prompts.
Request IDs let vendor support find your call. Cost per call, per user and per feature catches runaway loops early. stop_reason tells you about truncation. For agents, traces link model call, tool call, model call; OpenTelemetry is the neutral standard. Security: stable trusted instructions in the system layer, everything else is data.
Part 5 · Real-world builds

Four systems companies actually ship

Customer support agent

Tools for orders and refunds · identity gate in code · refund limit routes to a human · structured handoff.

Multi-agent research

Orchestrator + subagents · every claim mapped to a source · conflicting data flagged, not hidden.

Document extraction at scale

Strict schema with nullable fields · validate and retry with feedback · Batch API for 50% off.

Coding agents for a team

Claude Code or Codex · shared conventions in CLAUDE.md / AGENTS.md · review in CI · least privilege.

Same building blocks every time: schema, tools, grounding, evals, guardrails, cost.
These four are real patterns, and each one matches an official Claude certification scenario. Build at least one end to end, ideally on both Claude and OpenAI. Notice that none of them is a novel model trick: they are ordinary software with an LLM in the right place, guarded by code and measured by evals.
